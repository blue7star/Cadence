# 契约：发布任务 + 子任务责任人（所有权转移模型）

> 状态：READY_FOR_REVIEW（2026-11-04，已交付实现，挂 `issues.md` #39-44 待复核；第 0 段 ⑨ 已按推荐「自动提醒」落地，用户 2026-11-04 认可「自动提醒做的很好」）
> 取代：`2026-11-03-阶段责任人.md`（那份暂缓稿的方向被本份改判——二级阶段不设责任人，只设三级子任务责任人）。
> 沿用：`2026-11-03-三级节点.md` 的 `id`/`pid` 结构与三条算法（进度按叶子、日历只出叶子、相邻按同层）。

## 0. 决策

### 已定（2026-11-04 用户拍板）

| # | 决定 |
|---|---|
| ① | 发布时承接人=自己 → 落 `special`，直接进自己的专项工作，不进承接台 |
| ② | 承接台合并成「接收」一个主动作，不再有"规划并承接/直接办理"二选一 |
| ③ | 一条任务同时有 **发布人** 与 **承接人**；接收后 **owner 转移**，发布人转为只读 |
| ④ | 子任务日期跟随父任务，责任人不能改期 |
| ⑤ | 发布人定的 **总截止点** `due_date` 不可被承接人改动 |
| ⑥ | **接收 ≠ 派发**。接收只做所有权转移；派发是承接人理完计划后的独立动作（见 1.5） |
| ⑦ | 承接人可自由编辑整条任务的节点，包括删掉发布人建的那些 |
| ⑧ | 「当作临时任务」这个选项删掉，接收一律转专项 |
| ⑨ | 派发之后承接人再改计划（改期/换人/新增/删除）→ **自动**写提醒进承接台，不再点一次按钮（2026-11-04 用户确认：「自动提醒做的很好」，见 0.7.0 实施） |
| ⑩ | **子任务责任人的入口不限页面**：发布弹窗能配，承接下来的活在自己的专项详情里也能配。理由是「整件事交给别人」和「分一段出去」是两个层级——前者转移任务归属、要走发布；后者只是分工、不转移归属，所以不需要另开一条任务（2026-11-04 用户问「要不要开这个口子」，定：开） |

### 决策理由（⑨）

一个"通知"按钮，第二次开始就一定会有人忘记点；改了不告诉责任人，比多出一条提醒严重得多。首次派发用显式按钮（有仪式感、能反悔），之后的变更自动进「有变动的任务」，这条通道不能靠人的记性。

### 决策理由（⑩）

不开这个口子的代价是：承接人接了活、要往下分工，只能回「发布任务」再建一条——同一条活被拆成两条，进度分两处看，名字还得起两遍。而所谓"专项变发布入口"的担心不成立：接管的人只能是承接人本人（`assignee_no` 仍锁死），子任务责任人拿到的是「分给你的子任务」那一块，不是「等你立项」。两条路交付的东西不同，不存在语义重叠。仍然保留的硬约束：只能选 `activated=1` 的人，和发布任务同一道门禁。

## 1. 任务（开工前填完才动手）

- **触发**：用户原话——「下派任务窗口，本意是向下发布任务……有些任务需要协作完成，领导发一个任务，其中很多子任务需要其他人/下属完成。三级子任务允许设置责任人，二级阶段不用设置。任务的承接人可以是自己，也可以是其他人。承接人是自己则进入自己的专项工作，是其他人则出现在他的承接台，他接受之后自动进入他个人的专项工作。三级子任务也会出现在对应人的承接台，然后他点击加入待办，就会默认以临时任务加入他的个人待办。」
  第二轮补充：「承接之后任务 owner 发生变化，发布人不可再编辑该任务……承接人可以更细致地规划，但不可改变发布人定的总任务截止点。」
  第三轮补充：「点接收这个按钮，不应该承接发布子任务的功能。习惯是承接人接收后进入专项，再对该任务进行规划编辑，另做一个派发/通知按钮。任务变更、新增、删除的提醒，记得在承接台做到位。」
- **要改的模块**：`server.js` 数据层（加两列 + 回填 + `stage_notice` 表）、`server.js` 可见性 `stateFor`、`server.js` 权限 `upsertTask`、`public/app.js` 状态层、发布弹窗、承接台、专项页、详情页、`public/index.html`、`_dev/e2e.mjs`。

### 1.1 三个人，三个字段

| 角色 | 字段 | 管什么 | 不管什么 |
|---|---|---|---|
| **发布人** | `publisher_no`（新增） | 发起、定总截止、在未接收时改派/撤回 | 接收之后不能改任何东西 |
| **承接人** | `assignee_no` → 接收后并入 `owner_no` | 整件事推进、拆阶段、派发、换人 | 不能改总截止 |
| **责任人** | `stages[i].who`（仅三级） | 只这一段：勾完成 | 改标题/改期/改别人那段 |

- **`owner_no` 语义变更**：从「我发起的」变成「现在归谁管、谁能编辑」。这是本次唯一一处旧语义被改写的地方，见 1.10 兼容。
- **「承接人」和「责任人」必须是两个词。** 同一层用同一个词，三个月后没人分得清「他承接的是整件事还是一小段」。
- **二级阶段没有责任人**（`pid` 为空的节点，`who` 强制 `null`）。要派人，就把阶段拆成子任务再派人——这是这套模型唯一的心智负担，界面必须直说。
- 读取一律走 `stageOwner(t, s) => s.who || t.assigneeNo`，不许各处散写。

### 1.2 数据模型（两列 + stages 五个可选字段 + 一张提醒表）

| 位置 | 字段 | 含义 | 回填 |
|---|---|---|---|
| `task` | `publisher_no` | 发布人工号 | 见 1.10 |
| `task` | `due_date` | **发布人定的总截止**，只有发布人能改 | `= end_date` |
| `task.stages[i]` | `who` | 子任务责任人；`null` = 跟随承接人 | 不填 |
| `task.stages[i]` | `whoAt` | **派发时间**；`who` 有值但 `whoAt` 为空 = 已指定、还没派发 | 不填 |
| `task.stages[i]` | `joinedAt` | 责任人点「加入待办」的时间 | 不填 |
| `task.stages[i]` | `doneBy` / `doneAt` | 谁、哪天勾掉的 | 不填 |

- 加列走 `ensureColumn`，老库直接可用；`stages` 是 JSON 列，**零迁移**。
- **`who === 当前承接人` 时一律存 `null`**：换承接人后这些子任务自动跟随，不会挂在旧人头上。
- 服务端兜底：`pid` 为空（二级阶段）或 `type` 不是 `assign`/`special` 时，`who`/`whoAt`/`joinedAt` 一律落 `null`。
- `end_date` 与 `due_date` 的关系：`end_date` 是承接人的当前计划，**不得超过 `due_date`**（`upsertTask` 里 clamp，超了回 `errors`）。

**提醒表 `stage_notice`**（只为一件事存在：承接台要能告诉责任人"这条变了"）：

| 列 | 含义 |
|---|---|
| `id` / `task_id` / `stage_id` | 定位到某一条任务里的某一段 |
| `emp_no` | 提醒谁 |
| `kind` | `dispatched` / `added` / `moved` / `reassigned` / `removed` |
| `summary` | 人话摘要，如「11-05→11-08 改为 11-10→11-14」 |
| `at` / `seen_at` | 产生时间 / 看过时间（`null` = 未看） |

- **删除节点也留一条墓碑**（`kind='removed'`），否则责任人的约定会凭空消失，而他不知道为什么。
- 这张表只写不改，`seen_at` 一旦落就不再生效；超过 30 天的清理掉（`maintain` 里顺手做）。

### 1.3 发布：承接人决定类型

```
发布（选承接人）
├─ 自己   → type=special，owner=assignee=publisher=我，intake=null，due=end
│            → 直接进「专项工作」；子任务还要我自己点「派发」才出去
└─ 他人   → type=assign，owner=publisher=我，assignee=他，intake=pending
             → 进他的承接台「等你立项」；子任务暂不派发
```

- 发布弹窗补「阶段与分工（可选）」区：`assign` 和 `special` 共用同一套阶段树（含「+子」和子任务责任人下拉），`temp` 不给。
  ——**领导要在发布那一刻就把活拆完、把人点完**。现在 `assign` 弹窗没有阶段区（0.5.0 的决定），这次补上。
- 发布是「指定责任人」，不是「派发」：`who` 落库，`whoAt` 留空，等承接人理完再派。
- 发布后 toast 说清去向：派给别人 →「已发布给 张三，等他在承接台接收」；派给自己 →「已放入你的专项工作」。
- **未接收前（`intake=pending`）发布人仍可改、可改派、可撤回**。这是唯一一个发布人还能编辑的窗口，不给就等于发错了没法收回。

### 1.4 接收 = 所有权转移（不派发、不派生）

| 动作 | 结果（一条任务，原地改） |
|---|---|
| **接收**（承接台主按钮） | `owner_no := 我`、`type := 'special'`、`intake_status := 'accepted'`；`publisher_no` 与 `due_date` 不动；`stages` 整棵原样带过来 |
| ~~规划并承接~~（生成派生任务） | **退役**。`source_id` 不再产生新数据 |
| ~~直接办理（留在当前任务里）~~ | 删掉 |
| ~~当作临时任务~~ | 删掉（决策⑧） |

- **接收只做一件事**：把这条任务换到"我名下可编辑"。它不进任何执行者的待办、不通知任何人。
- 为什么改成转移而不是派生：发布人必须继续看到进度，而一条任务只能有一个 owner。派生能做到，但代价是两份计划、两处出现、进度靠 `source_id` 追。转移只有一份，天然同步。
- **`source_id` 链路退役**：`carried` 挂载行、`acceptedList`（已承接列表）、issues #20 的重复展示一并消失。老数据仍有 `source_id`，见 1.10。
- 接收后承接人**能改**：标题、计划起止（`end_date ≤ due_date`）、状态、增删任何节点（含发布人建的）、设/换子任务责任人。
- 接收后承接人**不能**：改 `due_date`、改 `publisher_no`。

### 1.5 派发：一个显式动作（决策⑥）

承接人接收后先在专项里理计划，理完再派出去。**派发之前，责任人的承接台一条都看不到。**

| 时刻 | 谁来点 | 结果 | 责任人承接台 |
|---|---|---|---|
| T0 发布（承接人=他人，`pending`） | — | 只是指定了 `who`，`whoAt` 空 | 不出现 |
| T1 承接人「接收」 | 承接人 | 所有权转移，进专项，**不派发** | 不出现 |
| T2 承接人理计划：改日期、拆段、填人 | 承接人 | 局部保存 | 不出现 |
| T3 承接人点 **「派发」** | 承接人 | 所有 `who≠null && whoAt==null` 的段一次性落 `whoAt=now`，各写一条 `dispatched` 提醒 | **一次性批量出现**，按父任务聚合成一张卡 |
| T4 责任人点「加入待办」 | 责任人 | `joinedAt=now`，生成 `temp`（带 `stageRef`） | 该条消失，活进他的待办与日历 |
| T5 责任人一直不点 | — | 卡片留着，标「等你 N 天」 | 保留（等于软拒绝，一期不做退回动作） |
| T6 派发后承接人又改了 | 承接人 | 自动写 `added`/`moved`/`reassigned`/`removed` 提醒（决策⑨） | 出现在「有变动的任务」块 |
| T7 父任务被删 | — | 批量写墓碑提醒 | 条目消失，留一条「任务已取消」 |

- **防呆**：详情页顶栏常驻一条「**有 N 段已指定责任人，尚未派发**」+ 派发按钮。不写这条，就会有人发布完以为派完了。
- **按父任务聚合**：一次派 5 段给同一个人，5 张卡是噪音。卡片标题用父任务名，副行写「分给你 3 段 · 最早 11-05 开始」，点开列明细。
- **自派（承接人=自己）也要点派发**，规则统一，不给特例。
- 承接人侧要能看见谁还没接：详情页每个子任务标「已派发 · 待加入（第 3 天）」/「已加入 · 11-06」。

### 1.6 变更提醒：承接台必须接住（决策⑨）

有了派发这个动作，"计划改了"就必须能被责任人看到，否则派发就成了一次性快照。

| 承接台里的位置 | 装什么 |
|---|---|
| **分给你的子任务** | 已派发、还没加入待办的段（按父任务聚合）；有未读变更的标「有更新」 |
| **有变动的任务**（新增块） | 已派发后发生的改期/换人/新增/删除，按任务聚合，每条一句话；点「知道了」清掉 |

- 变更摘要必须是人话：`「整理数据」11-05→11-08 改为 11-10→11-15`、`「写总结」已从这条任务移除`、`你被换成 李四 负责「做访谈」`。
- **删除节点不能只是消失**：留墓碑，让责任人知道自己那条预约没了。
- 提醒只在**承接台内**，不做站外推送、不做未读红点轰炸；承接台角标 = 待接任务数 + 未读变更数。
- 已加入待办的段被判改期时，`temp` 的日期同步跟着变（决策④），并在 temp 上标一次「计划已调整」。

### 1.7 状态同步：只有一个权威源

| 动作 | 结果 |
|---|---|
| 勾 temp 的完成 | 回写 `stages[i].done/doneBy/doneAt`；父任务进度按叶子重算 |
| 勾父任务里的子任务 | 同步把对应 temp 置为 `done` |
| 取消勾选 | 两边一起退 |
| 删 temp | **只断链，不删子任务**（否则上级的计划会凭空少一段） |
| 删子任务 / 删父任务 | 连带删 temp，并写墓碑提醒 |
| 改日期 | 只认父任务的子任务日期；带 `stageRef` 的 temp 禁止拖动、禁止改期 |

- 权威源是 `stages[i].done`，temp 的 `status` 是镜像；同一事务里两边一起写。
- 逾期各自判、互不传导：temp 按子任务日期判，父任务按 `due_date` 判。
- `stageRef` 幂等：同 `(taskId, stageId)` 只允许一条 temp，已存在时按钮显示「已在待办」。

### 1.8 连带规则

| 事件 | 处理 |
|---|---|
| 责任人换人 | 删旧 temp；旧人收一条 `reassigned` 提醒，新人重新派发 + 重新点「加入待办」 |
| 责任人被停用（`emp.active=0`） | temp 保留，详情页标「责任人已停用」，不自动改派 |
| 发布人在未接收时改派 | `assignee_no` 换人，`who` 不变；原承接人的「等你立项」条目消失 |
| 发布人在未接收时撤回 | 整条删除；若已派发过（自派场景）连带写墓碑 |
| 接收后发布人想改 | 只能改 `due_date`；其余走线下沟通 |

### 1.9 可见性与权限

| 谁 | 能看 | 能改 |
|---|---|---|
| 发布人（`publisher_no`） | 全部，含接收后的进度 | `pending` 时全部；接收后只 `due_date` |
| 承接人（`owner_no`） | 全部 | 除 `due_date` 外的全部（决策⑦：节点可自由增删） |
| 子任务责任人（`who`，且已派发） | 父任务**全文只读**（含别人的阶段，协作上下文） | **只有自己那段的 `done`** |
| 其他 | 无 | 无 |

- `stateFor()` 追加两条过滤：`publisher_no = me`、任一 `stage.who = me && whoAt` 非空。后者是 JS 侧过滤（`stages` 是 JSON 列，SQL 过滤不到），千人以内可接受，写进 `DEVELOPMENT.md`。
- **未派发的 `who` 不产生任何可见性**——指定了人 ≠ 交出去了。
- 子任务责任人**不进日历**：他日历上出现的是自己那条 temp。父任务不因「我负责其中一段」而进 `isMineTask()`——不然同一天两条。
- 知情人（`task_observer`）与责任人互不干涉；同一人既是知情人又是责任人时按责任人走（多一条能勾的）。

### 1.10 老数据兼容（零迁移，但不能失忆）

`ensureColumn` 加两列后按规则回填一次（写 `op_log` 记一条 `migrate:owner-publisher`，只跑一次）：

| 老行的情况 | `publisher_no` | 表现 |
|---|---|---|
| 普通任务（无 `source_id`） | `= owner_no` | 与现在一致：自己的任务，自己发布 |
| 老派生任务（有 `source_id`，0.5/0.6 的"规划并承接"产物） | `= 源任务的 owner_no` | 仍显示「承接自 XX」，但不再产生新链路 |
| 老原任务（被某条 `source_id` 指着的） | `= owner_no` | 在「我发布的」里标「**旧版承接（只读）**」并折叠 |

- `due_date` 一律回填成 `end_date`，所以老任务"总截止"= 当前计划，不会有新的拦截。
- 老 `who` 字段本来就不存在 → 全部视为"未指定责任人"，不触发派发。
- `assignee_no` 保留（未接收时是"被派的人"，接收后 `= owner_no`），避免动前端所有读取点。
- 已知瑕疵：老原任务与派生任务同时存在，发布人点进去看到的是接收那一刻冻结的计划。**不修**——新流程不再产生这种行，历史数据按原样展示并在列表里标"旧版"。

### 1.12 不变量

1. 老数据（无 `publisher_no`/`due_date`/`who`/`stageRef`）的进度、日历、详情显示与现在**完全一致**。
2. 派人只有两个入口：任务级 `assignee_no`，节点级 `stages[i].who`，没有第三条路。
3. `owner_no` 是唯一编辑权判据；发布人接收后只读，只能改 `due_date`。
4. `end_date ≤ due_date` 永远成立（服务端 clamp，不靠界面拦）。
5. `type==='assign'` 且 `assignee===owner` 的行**不存在**（服务端强制转 `special`）。
6. 二级阶段永远没有责任人；`who` 只在 `pid` 非空的节点上生效。
7. `who === 承接人` 存 `null`：换承接人后这些子任务自动跟随。
8. **没派发（`whoAt` 为空）的指定，不产生任何可见性、不产生任何待办。**
9. 一条子任务最多一条 temp（`stageRef` 唯一），勾选状态两侧同源。
10. 派发之后的每一次计划变更，责任人都能在承接台看到一条可读的提醒（含删除墓碑）。
11. 派的活一定有人收到：任务级和子任务级都拦 `activated=0`，文案一致。
12. 发布人对派出去的任务**始终能看到进度**，不需要靠派生副本。

### 1.13 明确不做

- 二级阶段责任人（旧稿方向，本份改判）
- 子任务多责任人（多人协作靠继续拆）
- 责任人退回/改派申请、改期审批流
- 接收后的"申请改总截止"流程（一期只能线下沟通，发布人手动改）
- 子任务落成独立 task 行（仍是 `stages` 里的一条）
- 第四级及更深、跨任务依赖
- 站外推送、未读红点轰炸（只在承接台内提醒）

### 1.14 验收（`node _dev/verify.mjs --full` 全绿 + e2e 新增断言）

1. 发布给自己 → 落 `special`（`owner=assignee=publisher=我`），专项页可见；
2. 发布给别人 → 落 `assign` + `pending`，承接人承接台「等你立项」可见；
3. 接收 → `owner` 转移、`type` 变 `special`、`intake=accepted`，**没有新任务行**，发布人侧同一条标「已移交」；
4. **接收后责任人承接台仍然为空**（派发前不可见）——这是决策⑥的核心断言；
5. 承接人点「派发」→ 该段进责任人承接台，且按父任务聚合只出一张卡；
6. 接收后发布人改标题/阶段被拒（`errors`），改 `due_date` 成功；
7. 承接人把 `end_date` 排到 `due_date` 之后被 clamp/拒收；
8. 发布时给三级子任务设责任人落库；给二级阶段直传 `who` 被落 `null`；
9. 加入待办 → 生成 temp 且 `stageRef` 正确；再点一次置灰（幂等）；
10. 勾 temp → 父任务该子任务 `done`+`doneBy` 同步；反向勾也同步；
11. 派发后改期 → 责任人承接台出现「有变动的任务」且摘要可读；点「知道了」后消失；
12. 派发后删节点 → 留墓碑提醒，责任人看到「已移除」；
13. 换责任人 → 旧 temp 删除、旧人收 `reassigned`；删父任务 → 关联 temp 全删；
14. 回归：老数据（含 0.5/0.6 的派生任务）的列表、详情、日历、进度与改动前一致。
