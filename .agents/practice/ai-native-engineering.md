## 观察（现象 + 根因假设，不下结论）

### 1. 门禁会重复它要禁止的错误

第一版「契约状态」检查只判「有没有写 `PASS`」。结果是一条合规通道被打开：
**永远不写 `PASS`**，全部停在 `READY_FOR_REVIEW`，门禁全绿。
这正是它想禁止的「没有证据算 pass」，只是换了一层皮。

根因假设：任何以「某事已发生」为条件的检查，如果没有定义「X 何时必须发生」，
就会退化成「没人自称违规」。检查的对象是**声明**，不是**事实**。

### 2. 「摘要排除文档」与「复核记录必须绑树」是两条互相拉扯的要求

把 `docs/` 排除出树摘要解决了自指（契约写摘要 → 摘要变），但复核记录本身就在 `docs/contracts/`，
于是可以在 `--full` 之后任意改写复核记录而不触发重跑。

根因假设：**「不改变运行行为的文件」和「不需要证据的文件」不是同一个集合。**
前者可以排除出代码摘要，后者不能排除出「证据是否新鲜」的判断。需要第二把尺子（evidenceDigest）。

### 3. 独立复核对单人项目可行且便宜，前提是给它一个入口

用独立子代理当 Reviewer：只读、只给「契约 + 代码 + 证据报告」、不给实现理由。
三轮里两轮打回，抓出的问题里有相当一部分是实现者自测永远发现不了的类型
（例如「台账把未修的记成已解决」）。

根因假设：实现者检查的是「我改的地方对不对」，复核检查的是「契约说的和你做的对不对得上」。
后者需要不同的输入集，换个上下文比换个问题有效。

### 4. 契约的「差异及原因」字段可以被编造，且机器无法发现

该字段不要求引用第 1 段原文。实测写过一条「契约原写 X」，而第 1 段根本没有 X；
两轮门禁 + 一次自测都没发现，是复核逐句对照原文才抓出来的。

根因假设：**自述类字段没有对账物，就等于没有约束。** 要约束它，必须让它可以被机器或人对照。

### 5. `fail_source` 分类变细之后，历史问题的归类会变

项目里有两条旧问题按 4 类口径记成 `review_miss`，按 7 类口径应该是 `machine_gate_miss`。
分类错了，改的对象就错了：前者改注意力，后者改断言。

根因假设：分类粒度决定修复对象。粒度不够时，不同根因会被折叠成同一个标签，修法必然打偏。

### 6. 完全落实：三个实测盲区被 skill 3.0.0 修复

2026-11-03 是「选择性采纳」——只取方法层（事实单一归属、契约、独立复核、fail_source），
**拒绝工具层**（`gate.py`、`agent_workflow.py`、`scaffold_project.py` 一律不用，见 `.agents/practice/adoption-log.md` 第 3/4 节）。
2026-11-04 转「完全落实」：工具层也接入，`.agents/gates/gate.py` 成为双轨门禁里的契约门禁。

当时拒绝 `gate.py` 的三个实测盲区，全部由 skill 3.0.0 修复，本项目已逐条对上：

| 当时的盲区 | 当时的实测现象 | 现在的修复 |
|---|---|---|
| ① 只比 `HEAD~1...HEAD` | M1/M3 看不见工作区与暂存区，门禁接错入口 | 新增 `--staged` 判 `git diff --cached`（索引区），pre-commit 拦「已 add 的受保护路径缺契约」 |
| ② 0 PASS 算通过 | `check_m2` 在 `checked==0` 时返回 `0 PASS events bound` 且 ok=true | `NOT_RUN`/`no_evidence` 一律退出 1，与「`NOT_RUN != PASS`」自洽 |
| ③ 只认 `VERSION` 文件 | 18 个版本的记录被读成 `0 version declaration(s)` | M4 支持 `version_authority: <path>`，本项目声明 `version_authority: version.js` 后 M4 PASS |

根因假设：这三条不是「用错了」而是「工具层没长全」——第一版只覆盖了「有账本、有契约的仓库」这条主线，
没覆盖「还没建账本 / 用自定义版本源 / 工作区有改动」这些真实分支。反馈把分支补上，skill 才从
「只能演示」变成「能真跑」。这是「反馈推动 skill 演进」的直接证据，留在账本里。

## 追加记录 · 2026-11-11 · 阶段区间误判：缺的是「不变量」这个位置

> 性质：新观察（append-only，不改上面任何旧条目）。对应 `.agents/issues.md` #64，`fail_source: invariant_gap`。

### 现象

任务「HR 数据底座（数据中台）」有五段跨年计划（2026-07-03 → 2027-06-30），段与段之间留了 11-07、11-08 这种正常空档。
新增一段 2026/11/07 → 11/08 被拒，提示「[五、受治理问数] 占到 6月30日，和 [数据实时接入…]（11月7日起）压上了；后者最早只能从 7月1日起」。
两段相差半年，却被判成重叠；建议的改法是把新段挪到 7 月 1 日之后；提示里的年份也丢了。

### 四层根因

1. **代码**：`validateStages` 规则 5 只比「数组里相邻的两项」（`list[i-1]` / `list[i]`），默认数组按时间有序；`stage-add` 又用 `push` 把新段放到末尾。于是新段只跟最后一段比：`'2026-11-07' <= '2027-06-30'` 成立 → 判重叠。文案用全站短格式 `fmt()`，年份丢失，「7月1日」是最后一段 end+1。
2. **入口**：五个写入口确实共用了 `validateStages`，但校验本身带着「数组有序」的隐含前提；按时间重排只发生在渲染层，落库顺序没跟着时间走，编号与时间脱钩。服务端 `upsertTask` 只校验「任务 end 不超 due」，对阶段区间零校验。
3. **测试**：e2e 只断言「合法的能存」「明显重叠的被拦」，用例挑的数据永远落在「相邻即相邻」的形态上：跨年 + 新区间在数组末尾 + 中间有合法空档，这个组合从没出现过；也没有断言报错文案里的段名与日期。
4. **体系（主因）**：`specs/modules/*.md` 有「不变量」章节（旧基线 app-ui 14 条、server-api 13 条、server-data 7 条、tooling 5 条、version 3 条，共 42 条），但**没有一条**规定「这条约束必须在服务端成立」或「必须有一条反例测试」——全是描述句，没有编号、没有拒绝点。`.agents/review-checklist.md` 的 B1-B11 里也没有任何一项问「领域约束在服务端成立吗」。`AGENTS.md` 第 2 节给了 Planner/Worker/Reviewer 的职责，没有一条覆盖「把领域约束写成不变量」；第 4 节 M8 的五个受理字段里也没有这一项。所以「谁来写、写到什么程度算完」从来没有答案。

### 为什么门禁全绿仍然漏

- `verify.mjs` / `gate.py` 判的是「有没有契约、有没有证据、这棵树跑不跑得通」，判不了「这条业务约束该由谁判定」。约束的**位置**不是机器能猜的。
- e2e 的绿证明「我挑的这几条路径对」，不证明「约束在系统边界上成立」。用例形态本身就是盲区。
- 前端校验存在，"有校验"这件事是真的；漏的是**判定权**和**反例义务**。这两件事此前没有任何一句话规定，所以无论跑多少遍门禁都不会红。

### 判定：`invariant_gap`，不是 `requirement_gap`

需求侧对「什么算重叠」没有歧义——闭区间相交，用户描述得很清楚，也没要求「必须在前端拦」。口径没缺，缺的是**承载口径的工程对象**：带编号、带服务端拒绝点、带 e2e 反例的不变量。
`requirement_gap` 的修法是「先补口径」；这里的修法是「把已经清楚的口径钉到系统边界上」，两者改的东西不同。

### 改进项（本轮已落地，不新增目录/门禁）

1. 五份模块蓝图各补 `INV-n`，每条必须写「拒绝点 + 反例」；`tooling` 的 INV-1 把元规则固定下来：只在前端拦的规则不写进「不变量」，改写进「公开行为」。
2. 服务端 `upsertTask` 增加 `checkStageIntervals`：同层区间相交、子段越出父窗口、任务周期 ≠ 一级阶段包络，三者直接拒收并回可读原因；只判「本次写入改变了区间」的请求，存量脏数据不挡无关编辑。
3. `.agents/review-checklist.md` 补 B12：本次涉及的领域约束，每条都要有服务端拒绝点与反例。
4. `AGENTS.md` 与 `.agents/issues.md` 的 `fail_source` 分类补 `invariant_gap`。
5. e2e 6.9：跨年空档放行、压中间段、压最后段、首尾相接放行、改期到原日期放行，以及三条「绕过界面直调 `/api/sync`」的拒收反例。

### 这次的方法结论（待第二个项目验证，不晋升）

不变量若只有描述、没有「拒绝点 + 反例」两个字段，它迟早退化成注释：写在谁都能改的前端函数里，绕过界面就失效。
判断一个约束有没有落地，只看一句话——**能不能举出一条绕过界面、被服务端拒绝的 e2e 反例**。

## 追加记录 · 2026-11-12 · 规则体系体检：先修 8 对矛盾
