# G2 复核清单

> 给**没参与实现**的人或新开的对话用。按顺序过，每条都要有结论（通过／不通过／不适用）。
> 清单里的每一条都对应 `.agents/issues.md` 里真实踩过的坑，不是通用模板抄来的。

## A. 先确认「评的是哪版代码」

| # | 检查 | 怎么查 | 为什么有这条 |
|---|---|---|---|
| A1 | 工作区里有没有混进与本次无关的改动 | `git status --short`，逐个问「这行为什么在这里」 | #9：七个版本堆在工作区没提交，混在一起后无法判断哪条改动属于哪次需求 |
| A2 | 上一轮的改动提交了吗 | `git log --oneline -3`，与 `delivery.md` 的改动清单、`task.md` 的候选范围对得上 | 同上。没提交的改动一旦被覆盖就没了 |
| A3 | 验的是不是当前代码 | `curl -s localhost:8788/api/version` 的 `semver` 是否等于 `version.js` 的 `SEMVER` | #11：e2e 跑的是服务启动时的旧代码，还报全绿 |
| A4 | 复核对象是不是精确候选 | `verdict.md` 的 `candidate_digest` 与事件流 PASS 事件的 `candidate_digest` 一致；`artifacts/runs/<task_id>/candidate-a<n>.patch` 存在且能复算哈希 | 防止「拿 A 版代码的证据评 B 版代码」。树变了只能新开复核写新结论，不改历史候选快照 |

## B. 不变量有没有被破坏

| # | 检查 | 怎么查 |
|---|---|---|
| B1 | 老数据库还能打开吗 | 备份 `data/workbench.db`，用旧库启动，登录、看日历是否正常 |
| B2 | 常规实例生成是否幂等 | 连续两次触发 `maintain`，实例条数不变 |
| B3 | 可见性四视角 | 依次切成 本人／下属／上级／无关同事，确认该看的能看、不该看的看不到，且只读页面真的不能改 |
| B4 | 日期算法边界 | 跨月（26 日起）、月末 31/30/28、闰年 2/29、周末与节假日、阶段跨月连续 |
| B5 | 状态与节点对齐 | `done` 全勾、`todo` 全放、`doing`/`paused` 至少留一个未完成；日历与清单说法一致 |
| B6 | 逾期判定 | 计划结束日已过且未完成 = 逾期；**已完成永不算逾期** |
| B7 | 同步冲突 | 两个标签页改同一条任务，先看谁覆盖谁，再对照契约里写的语义 |
| B8 | **界面说不说得清「我是谁」** | 打开每个新改的输入区，逐行问一句：这一行是阶段还是子任务？加了之后落到哪里？选这个人会发生什么？**答不上来就是没做完**，不管断言多绿。两个长得一样的框并排出现，一律算缺陷（#48） |
| B9 | **同一件事的能力在各入口一致吗** | 新建弹窗能做的，详情页能不能做？（#47：弹窗有「谁做」，详情页没有，用户当场卡住）同一个动作如果两处各写一份 UI，按「迟早会漏」处理 |
| B10 | **点这一下，用户接下来想干什么** | 对每个可点的元素问一句：人为什么点它？点完他要去哪儿？**点完落到「下一步动作」那里，而不是落到「说明这是什么」那里**。（#61：日历上点一条活直接弹整页详情，而人多半是想改状态——把人从日历赶走，再让他自己找路回来）顺手再看：这一下点完，有没有别的东西替他做决定、把他刚点开的东西冲掉 |
| B11 | **可见界面改动留没留证据** | 只要动了界面，必须先**截图自审**（视口宽度与 `_dev/e2e.mjs` 的 `--window-size` 一致，当前 1600×1000；改前改后各一张），**逐条列出看出的问题**——入口在哪、点几下到、要不要滚才看得见；确实没问题也要写「看了 X 屏、无问题」。截图与问题清单放 `artifacts/runs/<task_id>/walkthrough/`，verdict 里写清看了哪几屏、哪一屏没过。只有一句「我走查过」不算 |
| B12 | **本次涉及的领域约束，每条都有服务端拒绝点与反例吗** | 对本次改到的业务对象，去看 `specs/modules/*.md` 的 `INV-n`：每条都得写明服务端在哪个函数拒（最好带提示原文），并在 `_dev/e2e.mjs` 找到一条「绕过界面、直接调接口」的反例证明它真的被拒。只在前端 `validate*` 里拦、服务端零校验的规则**不算不变量**——绕过界面就失效的约束等于没约束（#64：阶段重叠只在 `validateStages` 里，直调 `/api/sync` 能写进任意重叠数据） |

## C. 证据是不是真的

| # | 检查 | 怎么查 | 为什么 |
|---|---|---|---|
| C1 | 断言有没有被放宽 | `git diff HEAD -- _dev/e2e.mjs`，看有没有删断言或改期望值 | 让测试变绿最省事的办法就是改测试，这是最隐蔽的自欺 |
| C2 | 视觉结论是量出来的还是看出来的 | 断言里是否有 `getComputedStyle` 的具体颜色值 | #14：截图看浅色小字看错过好几次 |
| C3 | 失败信息能否定位到函数 | 故意改坏一处，跑一次，看报错是否指出「哪个函数算错了」 | 报「界面不对」等于没报（#12） |

## D. 收尾

| # | 检查 |
|---|---|
| D1 | `.agents/issues.md` 里这次涉及的问题，状态更新了吗？新问题登记了吗？ |
| D2 | `fail_source` 标对了吗？同一个标记连续出现两次，规则要改，不是代码要改 |
| D3 | 版本按 semver 递增了吗？修复 bump Z、新能力 bump Y、破坏性变更 bump X（0.x 阶段可用 Y）；`version.js` 登记并跑 `--write` |
| D4 | `verdict.md` 填完了吗？（缺字段 / `evidence_status=NOT_RUN` / `not_run_count>0` = 这次复核没发生） |
