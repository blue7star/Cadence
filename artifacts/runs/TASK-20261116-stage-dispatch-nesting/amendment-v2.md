# 契约变更 v1 → v2（2026-11-16）

用户回话（原样引用，仅取决策句）：

「1. **列名用「父任务阶段编号」**，避开第 25 列已有的「父阶段编号」，同文件不允许两列同名。另一列仍是「父任务编号」。
2. **「一级可以设阶段责任人」按你的读法**：一级**任务**的阶段可以设责任人；一级阶段本身不带负责人，不改 `applyStageOwners` 清空一级 `who` 的那段逻辑。派发入口仍只在二级节点（`pid` 非空）上。
3. **新增：待接收状态必须可撤回或改派**。理由是派错就成死路——对方不收，父阶段永久挂「待接收」，只能删段重建。范围限定在接收前：父方可以撤回这次派发（父阶段回到未派发、pending 子任务删掉或标记作废），也可以改派给另一个人。**已接收之后的换人/撤回不在本轮范围**，但要写进已知限制，不要在文档里假装支持。」

「另外：partial unique index 代替冗余单列索引这件事我认可，按你的做法来，但要在 `server-data.md` 里写清"唯一约束即查询索引"，免得下一个人以为是漏建。」

## 落进契约的变化

- 契约 v2：`contract_version: 2`。
- 命名争议关闭：导出末两列 = `父任务编号`、`父任务阶段编号`。
- 阶段负责人边界关闭：只放开「任务级」分层；`applyStageOwners` 清一级 `who` 的逻辑不动；派发入口仍只认 `pid` 非空节点。
- 范围新增：`POST /api/task/undispatch`（接收前撤回）、`POST /api/task/dispatch` 带 `stageId+who` 时改派（仅 pending）。
- 明确排除并写入已知限制：已接收子专项的换人/撤回。
- `server-data.md` 必须写明：partial unique index 左前缀即 `parent_task_id` 查询索引，不另建冗余单列索引。
