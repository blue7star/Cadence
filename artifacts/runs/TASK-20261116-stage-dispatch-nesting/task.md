## 目标与范围

- 业务目标与用户可见的成功：
  - 在任务详情里把一段派给某人 → 对方承接台出现「等你立项」一条待接收；他接收后它成为一条独立专项，能自己拆阶段、排期、往下派一层；派活的人在自己的任务里只看到这一段的状态与进度汇总。
  - 任何人在自己的列表里都不会因为「派发」而看到同一条活两次。
  - 父阶段的完成与否只由子专项决定，父方勾不动；子专项最多三层，第四层在服务端被拒、界面上按钮禁用并说明原因。
- 范围内：
  - **数据模型**：`task` 增 `parent_task_id` / `parent_stage_id`（可空，老行全空）；`UNIQUE(parent_task_id,parent_stage_id) WHERE parent_task_id IS NOT NULL AND parent_stage_id IS NOT NULL`（该唯一索引左前缀即 `parent_task_id` 查询索引，不再另建冗余单列索引）；新流程**不写** `stage_ref`。
  - **派发**（`POST /api/task/dispatch`）：对每个 `pid` 非空、有 `who`、尚无 `whoAt`、且尚未关联子任务的段，建一条 `type=assign`、`owner_no=派发人`、`publisher_no=派发人`、`assignee_no=who`、`intake_status='pending'` 的子任务，带 `parent_task_id`/`parent_stage_id`；随后把父阶段的 `who/whoAt/joinedAt/done/doneBy/doneAt` 全部清空（责任转移到子任务）。深度 = 父深度 + 1，> 3 整次拒绝（不部分派发）。
  - **撤回 / 改派（仅接收前）**：`POST /api/task/undispatch {id, stageId}` → 仅父任务 owner、仅 `intake_status='pending'` 的子任务：删掉这条 pending 子任务，父阶段恢复为「已指定、未派发」（`who` 还原成子任务的 `assignee_no`，`whoAt=null`）。`POST /api/task/dispatch {id, stageId, who}` → 该段已有 pending 子任务时，只把 `assignee_no` 改成 `who`（一次完成改派）；已接收的子任务一律拒绝。
  - **接收**（沿用 `/api/task/accept`）：所有权转移 + `type=special`，父引用保留；接收前不进对方日历（现有 `isMineTask` 已排除 pending assign，不改）。
  - **完成态**：父阶段不落 `done`。读侧由子专项派生 `done/doneBy/doneAt`；写侧（`/api/sync` 整段提交、`/api/stage/toggle`）一律以子专项为准，父方硬拒，文案沿用「这一段由别人负责，只有他能勾完成」。
  - **状态上行**：子任务状态/阶段变化 → 重算父任务 `status`（沿用 `stageStatusFromLeaves` 口径，派出去的叶子按子专项 `status` 计）；done 翻转时写 `stage_notice(kind=stage_done)`，文案与现有一致。
  - **可见性**：`parent_task_id` 非空的行只从「我是 `owner_no` 或 `assignee_no`」进入；`publisher_no`、`owner_nos`（下属常规/专项）、`source_id`、`stageWhoMe` 四条来源对子任务一律不成立。子专项仍可设知情人（决策 5）。
  - **透视**：`state` 里父任务的阶段上挂 `child` 摘要 `{id,title,status,intakeStatus,progress,ownerNo,assigneeNo,start,end}`；不返回子任务的 `stages`；子任务行对派发人不可见，故派发人拿不到二级阶段、也拿不到三级。
  - **删除**：删父任务 → 先把子任务的 `parent_task_id/parent_stage_id` 清空（脱钩，不级联删），对已接收的子专项写一条「父任务已取消，你负责的这条已成为独立专项」提醒；父任务里某一段被删 → 同样脱钩，不删子任务。
  - **进度**：派出去的叶子按 `child.progress/100` 计，父任务进度 = 所有叶子折算后的平均；服务端提供 `progressOf(row)` 供 `child.progress`，前端 `taskProg` 同口径。
  - **导出**：追加两列到末尾、共 27 列——`父任务编号`、`父任务阶段编号`（见「已批准的 L0-L2a 决策」第 3 条：不能叫「父阶段编号」，与既有阶段级列重名）；子任务行填、顶层行空、续行留空。被派发的阶段：`阶段负责人`/`阶段完成`/`阶段完成日` 改读子专项（派生），不落回 `stage.who`。
  - **前端**：父阶段行显示「待接收 / 子专项状态 + 进度」，待接收时给「撤回」与「改派」；接收后不再出现「谁做」下拉与勾选框；第三级隐藏可派发的入口并禁用「派发」按钮，给一句为什么；子专项详情显示「来自「父任务」的「某段」」。
  - **已知限制（写进文档，不假装支持）**：子专项一旦被接收，父方不能换人、不能撤回，也不能删段带走它——只能由子专项负责人自己继续维护。
  - **版本**：0.11.0（Y），`node version.js --write` 生成 CHANGELOG。
- 范围外：见元信息 `out_of_scope`。
