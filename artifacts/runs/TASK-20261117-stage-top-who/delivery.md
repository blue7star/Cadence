# 交付说明 — 一级阶段行直接设责任人（v0.12.0）

task_id: TASK-20261117-stage-top-who
contract: v1（`task.md`；相对 `TASK-20261116-stage-dispatch-nesting` 的 v2 只扩展**入口位置**，不改状态机）

## 做了什么

1. **一级阶段行「谁做」入口**：任务详情左栏的一级阶段行，在「任务为 `assign/special`、`depth < 3`、这一段未完成且还没有任何子任务」时，直接显示可见的「谁做」标签 + 下拉。选中同事后**一步**完成原来「+ 子任务 → 填名 → 选人 → 派发」四步。
2. **一步生成并派发**（`POST /api/task/dispatch` 新增 `{id, topStageId|topIndex, who}`）：服务端先为一级阶段生成一条**同名、同起止**的二级节点，再走既有派发循环落成 `type=assign`、`intake_status=pending`、带 `parent_task_id/parent_stage_id` 的子专项，并照旧清空二级节点的 `who/whoAt`。一级阶段自身不落 `who`。
3. **入口互斥**：派完/已有子任务的一级行不再渲染「谁做」，改派与撤回只留在二级行（`2.1 待接收 / 改派 / 撤回`），两个入口不会同时改同一段。
4. **服务端拒绝点（INV-5）**：非 owner、`depth+1 > 3`、找不到阶段、`pid` 非空、已完成、已有子阶段/子专项、`who` 为空、花名册外/未登录、任务类型非 `assign/special`——逐条给可读原因；不依赖前端隐藏。
5. **老数据兼容**：0.11.0 之前的一级阶段可能没有 `id`。派发时服务端补一个 `sp_...` id，再让子专项的 `parent_stage_id` 指向它；表结构不变。演示库 `1002_sp1` 实测可派。
6. **文案**：阶段卡片与任务信息里的引导改成「整段交给别人直接选『谁做』；要拆成几段再点『+ 子任务』」。

## 判断与取舍（请重点看这条）

- **已有子任务的一级行不再出现「谁做」**。严格遵守了「二级行沿用现有下拉、两个入口不打架」；否则同一段会在两行各有一个负责人入口，改哪边都说不清。代价：想把一段拆给 3 个人，仍走「+ 子任务」多条子任务；整段只给 1 个人，用新下拉一步到位。
- **已完成的一级段不允许再派**（服务端拒「先取消完成」），避免给已完成段换人后完成态被冲掉。
- **落点仍是二级节点**：上一轮「派发入口仅开放给二级节点（`pid` 非空）」在**入口层**被本条扩展为「一级行可直接发起」，但 `who`、子专项、完成态仍全部落在二级节点上；`applyStageOwners` 继续清一级 `who`，三层封顶、导出父子列、可见集来源、单份完成态均未改。
- 没有新开状态机：仍是 `dispatch → accept → syncParentFromChild` 同一条通道。

## 已知限制（本轮明确不做）

- 旧数据里已经 `whoAt` 置位的二级段仍走旧「加入待办」通道，不迁移、不改写；这类任务的一级行可能因为已有子任务而不显示新入口（责任在二级行）。
- 已接收子专项的换人 / 撤回仍不支持。
- 已接收子专项的父阶段不再显示新入口（这段已经有子阶段，符合互斥规则）。
- 不做父阶段与子专项的日期联动；子专项自己的计划归负责人。
- 第三级任务不显示入口，服务端同样拒；临时任务不显示，服务端同样拒。
