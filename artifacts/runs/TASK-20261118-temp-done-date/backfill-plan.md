# 存量补数方案 — 临时任务完成日期（未执行，待确认）

- 影响范围（真实库只读统计，2026-11-18）：`type='temp' AND status='done' AND done_at IS NULL` 共 **1 条**。
- 本轮代码上线后，这 1 条的导出「完成日期」会保持为空，不会伪造日期。

## 方案 A（推荐）：不补，历史留空

- 做法：不做任何 UPDATE。
- 结果：该条历史任务导出「完成日期」为空；从本次上线起的临时任务都有真实完成日期。
- 优点：零造假、零风险；缺点：历史那 1 条永远缺这个值。

## 方案 B：用 `updated_at` 作为「最后写入时间」的近似值，并明确标注来源

- 候选 SQL（**未执行**）：

```sql
-- 仅限：无阶段、已完成、done_at 为空
UPDATE task
   SET done_at = substr(updated_at, 1, 10)
 WHERE type = 'temp'
   AND status = 'done'
   AND (stages IS NULL OR stages = '[]')
   AND (done_at IS NULL OR done_at = '');
```

- 结果：那 1 条会得到类似 `2026-11-12` 的日期（`updated_at` 的日期部分，UTC 存储，需按 Asia/Shanghai 换算后再写）。
- 风险：`updated_at` 不等于完成时刻。若完成之后又改过标题/分类，补出来的日期会偏晚；这属于「有来源的近似值」，不是真实完成日期。
- 如果选 B，需要先确认这 1 条在完成之后确实没有再被编辑过；否则不建议。

## 方案 C：根据 `op_log` 里的 `sync` 记录推断

- 现状：`op_log` 的 `sync` 只有 `rows=N`，没有任务 id/字段明细，无法可靠判断「哪一次 sync 把这条任务切成 done」。
- 结论：不可行，除非以后给 sync 日志补充任务 id 与状态变化明细（不属于本轮范围）。

## 建议

- 默认按方案 A：不补。历史留空是可接受的真实状态；本次上线后的完成日期全部由服务端在状态迁移时记录。
- 若你明确要求历史那条也要有值，再按方案 B 执行，并在交付说明里标注「该日期来自 updated_at 近似」。
