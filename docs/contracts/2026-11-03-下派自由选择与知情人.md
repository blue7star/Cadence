# 契约：下派可自由选人 + 专项可指定知情人

## 1. 任务（开工前填完才动手）

- **触发**：用户原话——「下派任务有一个限制，必须选择直属上级才能发布任务。取消这个限制……现在不是可以自由对一个人下发任务嘛，保留这个实现，然后在创建专项任务的时候，支持可以选择知情人……现在对下派任务导航页进行规范一下……新增下属专项工作推进情况和我关注的任务两个模块……如果下发/选择知情人的对象目前还没有登录使用过工作台……我的建议是下发阻断，知情人不阻断」。
- **要改的模块**：`server.js` 数据层、`server.js` 可见性、`server.js` 同步、`public/app.js` 状态层、`public/app.js` 下派页、`public/index.html`（样式）。
- **不变量**（这次绝不能被破坏的）：
  1. **下派出去的活，下派人必须能看到进度**——「我下派的任务」里能看到承接人、阶段进度、逾期；对方承接后派生出来的任务（`source_id` 指回）仍然挂在下面。
  2. **专项、临时任务仍然只归自己办**（`owner_no = me`），本次不动这条；知情人只是"知情"，不因此获得执行权。
  3. **别人的任务一律只读**：知情人、下属、上级看别人的任务都不能改字段（`canEdit` 判定不变）。
  4. **老数据零迁移**：已有 `data/workbench.db` 直接可用，不需要重建库、不需要重新导入花名册。
  5. **不把知情人塞进承接链路**：知情人不会出现在任何人的「下属」列表里，也不会因此收到待接收任务。
- **明确不做**（范围外）：
  - 不做"知情人可以评论/催办/回复"——知情人只**看**，不参与流转。
  - 不做「关注」的通知推送（关注仍然只是本人在页面上的一层视图偏好）。
  - 不做下派对象可以是"外部人员/未在花名册的人"——承接人必须在花名册里。
  - 不改「任务承接台」「下属常规工作推进」的既有口径，只在「下派任务」页加两个模块。
  - 不动阶段责任人（`2026-11-03-阶段责任人.md` 那份仍然暂缓，本次不做阶段级责任人）。
- **验收**：`node _dev/verify.mjs --full` 全绿；界面上看到「下派任务」页有四个模块、承接人下拉能选到非直接下属、给未登录过的人下派被拦住、给专项选知情人后知情人能在「我关注的任务」里看到进度。
- **版本**：**bump Y**（0.5.1 → 0.6.0）。这是新能力成批上线：下派对象范围放开、知情人、关注任务聚合。

### 1.1 「谁登录过」这件事怎么记

现在的 `emp` 表只有工号、姓名、岗位、部门、上级、启用标记，**没有"这个人用过工作台没有"**。这是本次唯一必须动数据表的地方。

| 字段 | 表 | 含义 | 缺省 |
|---|---|---|---|
| `activated` | `emp` | `1` = 至少登录过一次 | `0` |
| `last_login` | `emp` | 最后一次登录时间 | `null` |

- **写入时机**：`/api/login` 校验通过的那一刻写 `activated=1`、`last_login=now`。
- **老数据回填**：迁移时用 `op_log` 里 `action='login'` 的 `actor_no` 反查，把登录过的人置为 `activated=1`。
  **不这么做的话，升级当天所有老同事都会被当成"没登录过"，下派全部被拦死**——这是本次最容易踩的坑。
- 花名册重新导入（`import-emp.js`）**不重置** `activated`：同一个工号还是同一个人，他登录过就是登录过。

### 1.2 下派：自由选人 + 未登录阻断

| 规则 | 内容 |
|---|---|
| 承接人来源 | **全员花名册**（不再限于直接下属）。下拉分两组：「我的下属」「其他同事」，非下属要标出来，让人知道这是跨级 |
| 不再要求 | **不要求下派人自己设了直属上级**；**不要求存在直接下属** |
| 阻断 | 承接人 `activated = 0` → **不让建**，并说清「他还没登录过工作台，派下去收不到」 |
| 不阻断 | 选知情人时同样的人 → **照常可以选**，只是提示一句 |

- 阻断口径：**服务端也要拦**。前端拦是给人看的，服务端拦是防脏数据绕过界面写进来。两边文案要一致。
- 阻断时的行为是「这条任务没建成」，不是「建成了但标红」。宁可少一条，不要一条没人接的活躺在列表里冒充进展。

### 1.3 知情人（专项任务）

| 规则 | 内容 |
|---|---|
| 在哪选 | **新建/编辑专项任务**时，表单里多一个「知情人」多选；先按**自由选择**（全员花名册，可搜索）做 |
| 存哪 | 新表 `task_observer(task_id, emp_no)`，联合主键。**不用 task 表加 JSON 列**——要按人查"我知道情了哪些任务"，JSON 列查不动 |
| 谁能看 | 知情人能看到该专项的**标题、阶段、进度、状态、起止**，**只读** |
| 在哪看 | 「下派任务」页 → 「我关注的任务」模块，标一句「XX 让你知情」 |
| 不做 | 知情人**不进**他的今日待办、不进他的日历、不进他的承接台；知情人**不可**承接、不可勾选、不可改任何字段 |
| 不阻断 | 知情人没登录过工作台也照样能选（知情是"知会一声"，不依赖对方账号） |

- 知情人的可见性**只走这一条路径**：不因为是知情人就扩大他在其他页面的可见范围。
- 专项任务可以有多个知情人；同一个任务重复添加同一人，忽略。

### 1.4 「我关注的任务」怎么来的

| 来源 | 数据 | 展示 |
|---|---|---|
| ① 主动关注的常规 | `watch` 表 `kind='routine'`（沿用现有 `rule_id`） | 下属名 + 常规名 + 当前节点 + 本周完成度 |
| ② 主动关注的专项 | `watch` 表 `kind='special'`（新增 `task_id`） | 下属名 + 专项名 + 阶段进度 + 状态 |
| ③ 别人让我知情 | `task_observer` 里有我 | 发起人 + 专项名 + 阶段进度 + 状态，标「XX 让你知情」 |

- **自己下发的任务不在这里**，仍在「我下派的任务」里——避免同一条任务在两个模块出现两次。
- 关注对象范围：主动关注只限**直接下属**（现有 `watch` 的 `sub_no` 语义不变）；越级关注走来源③。
- `watch` 表加两列：`kind`（`'routine'` / `'special'``，默认 `'routine'`）、`task_id`（专项 id）。
  **老数据 `kind` 为空按 `'routine'` 处理**，不重写老行。

### 1.5 「下派任务」页的四个模块（顺序固定）

1. **我下派的任务**（原有，不动）
2. **下属常规工作推进情况**（原有，不动）
3. **下属专项工作推进情况**（新增，**默认折叠**，实现方式与 2 类似：按成员列专项，可展开看阶段）
4. **我关注的任务**（新增）

- 模块 3 的折叠粒度：**整块默认收起**，标题行点一下展开；展开后按下属逐条列出他的专项。
- 模块 4 默认展开（有内容才显示，空态写清楚「关注某个下属的常规/专项，或别人让你知情的专项，会出现在这里」）。

### 1.6 接口形状变化（`/api/state` 与 `/api/sync`）

| 位置 | 变化 | 兼容 |
|---|---|---|
| `/api/state` → `roster[]` | 每个元素多 `activated: boolean` | 纯新增，老前端忽略即可 |
| `/api/state` → `tasks[]` | 专项任务多 `observers: string[]`（知情人工号）；**我作为知情人的任务多 `observer: true`** | 纯新增 |
| `/api/state` → `watch[]` | 每条多 `kind`、`taskId` | 纯新增；老行 `kind` 缺失按 `'routine'` |
| `/api/sync` 请求体 `tasks[]` | 多 `observers: string[]` | 纯新增；**只有任务 owner 的提交才生效** |
| `/api/sync` 请求体 `watch[]` | 多 `kind`、`taskId` | 纯新增 |
| `/api/sync` 响应 | 多 `errors: string[]` | 纯新增；**有错误时那条任务没写进去**，前端要把第一条错误 toast 出来 |

- **`/api/sync` 是增量合并**（只提交变化行）。新增字段没变时不会出现在请求体里，所以服务端要保证「字段缺失 ≠ 清空」：
  `observers` **只有在该任务本轮确实出现在请求体里时**才整体替换；不在请求体里的任务，知情人名单原样保留。
  （与 `applySync` 现有的"后写覆盖"语义一致，不引入新语义。）
