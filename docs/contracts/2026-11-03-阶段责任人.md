## 1. 任务（开工前填完才动手）

- **触发**：用户原话——「下发的任务……阶段任务和子任务也可允许设置责任人」；讨论后决定**先不做第三级**，只做「阶段可设责任人」这一层。
- **要改的模块**：`server.js` 数据层、`server.js` 可见性、`server.js` 同步、`public/app.js` 状态层、`public/app.js` 日历、`public/index.html`（样式）。

### 1.1 结构（只加一个字段，不迁移）

`task.stages` 元素新增三个可选字段，**数组仍是扁平的，不引入 `pid`／父子关系**：

| 字段 | 含义 | 缺省 |
|---|---|---|
| `who` | 阶段责任人工号 | `null` = **跟随任务承接人** |
| `doneBy` | 勾掉这个阶段的人 | `null` |
| `doneAt` | 勾掉的日期 `YYYY-MM-DD` | `null` |

- **`who = null` 表示「跟随承接人」，不要写死工号。** 承接人换人时，跟随的阶段自动跟着走；写死了就会挂在旧人头上，这是最容易漏的坑。
- 老数据没有这三个字段 → 全部按 `null` 处理，**零迁移**。
- 读取一律走同一个兜底函数 `stageOwner(t, s) => s.who || t.assigneeNo`，不许在界面各处散写 `s.who || t.assigneeNo`。

### 1.2 权限（一条规则，不新增概念）

| 谁 | 能改什么 |
|---|---|
| `owner_no` 或 `assignee_no` | 全部：标题、日期、状态、增删阶段、**设阶段责任人** |
| 阶段 `who === me`（且不是上面两者） | **只能勾自己那个阶段的 `done`** |
| 其他 | 无 |

- `type !== 'assign'`（专项 / 临时）→ 所有阶段的 `who` 强制 `null`；前端不渲染下拉，复用现有 `.locked` 样式与「要交给组员，请用『下派任务』」的说明。
- 与任务级承接人规则**完全一致**——派人只有一个入口，这条不是新规则，是多用一次。
- 可勾判定：`canTick(t, i) = canEdit(t) || stages[i].who === me`。前端与 `upsertTask` 共用这一个判定。

### 1.3 可见性

`stateFor()` 的过滤条件追加一条：任务里有任一阶段 `who === me` 时，该任务进入可见集。

- **不裁剪 `stages`**：阶段责任人能看到整条任务的全部阶段（3~5 段），知道上下游在干什么、自己该等谁。上一版讨论里曾打算裁剪成「只看自己那段」，这里改判——同组的人本来就互相知道在做什么，裁剪只会让详情页变空、还要多解释「为什么别人那段是灰的」。真有保密需求的专项，本来就不该派给组员。
- 节点责任人对整条任务**只读**：不进 `canEdit`，改不了任何字段。
- 分类、优先级、达成标准都可见（协作上下文，不敏感）。

### 1.4 承接时序（别让人看到两份同一件事）

| 父任务状态 | 阶段责任人 |
|---|---|
| `intakeStatus = 'pending'`（上级刚派、还没被接） | **收不到**，不进待办、不进承接台 |
| 承接后（`accepted` 或直接办理） | 生效 |

与现有「未承接的下派任务不进下属今日待办」同一条逻辑，否则承接台会同时出现「待接收的整条任务」和「我负责的阶段」。

### 1.5 页面改动清单

| 位置 | 改什么 |
|---|---|
| 新建／编辑任务弹窗 | `assign` 类型每个阶段行加「责任人」下拉：`跟随承接人`（默认）+ 我 + 直接下属；`special`/`temp` 不出现 |
| 任务详情页（整页） | 左栏每个阶段行右侧显示责任人名字；不是自己那段时勾选框置灰并给出「由 XX 负责」的说明 |
| 任务承接台 | 新增一块**「我负责的阶段」**：`父任务 · 阶段名 · 时间`，点进详情，能勾自己那段 |
| 今日待办 | 阶段责任人的条目平铺出现，标题 `父任务 · 阶段名`，可直接勾（不加这条，他根本看不到今天该干什么） |
| 日历 | 不动算法，只把 `isMineTask()` 追加一条「任务里有阶段 `who === me`」 |
| 详情页阶段行 | 勾掉后显示 `doneBy` + `doneAt`（如「李明 · 11-05 勾掉」），让总负责人一眼看到是谁、什么时候推进的 |

> 最后一条是这次**性价比最高的改动**：不加它，总负责人只能看到「3/5 完成」，看不到谁干的、什么时候干的，等于多人协作只做了一半。成本就是三个字段。

### 1.6 算法：这次零改动

- **进度不用改**：两级就是「阶段数做分母」，没有父阶段重复计数的问题。`taskProg()` 原样。
- **日历不用改**：`occOn()` 本来就按阶段出条目，阶段已经是最细一级。只改 `isMineTask()` 的可见判定。
- **拖动不用改**：`dragCheck()` 仍只看 `owner_no`／`assignee_no`，阶段责任人没有改期权（改期是计划权，归总负责人）。

这正是「先不做三级」换来的：**数据结构、进度、日历、拖拽四条最贵的逻辑全都不用碰。**

### 1.7 不变量

1. 老数据（`stages` 无 `who`/`doneBy`/`doneAt`）的进度、日历、详情页显示与现在完全一致。
2. 派人入口仍只有一个：`type !== 'assign'` 时所有 `who` 强制 `null`，前端不给下拉，服务端兜底。
3. 阶段责任人只能勾自己阶段的 `done`，改不了任何字段，也改不了别人的阶段。
4. `who = null` 的阶段跟随承接人：换承接人后，这些阶段自动落到新人头上。
5. 上级对「下属承接后的任务」仍只读（`source_id` 链路不松动）。
6. 未承接的 `assign` 任务，阶段责任人收不到任何提示。

### 1.8 明确不做

- 第三级子任务（结构与视图都不留入口，将来要加是 `pid` 字段 + 一轮 e2e 的事）
- 节点级承接 / 接收 / 退回状态机
- 改期申请与审批流
- 站内通知与推送、未读角标（一期无推送，靠承接台与今日待办兜住）
- 跨层指派（阶段责任人只能选**直接下属**，要给下属的下属派，由他承接后再分）
- 节点级交付物、附件、评论

### 1.9 验收

`node _dev/verify.mjs --full` 全绿，e2e 新增断言：

1. 下派任务新建阶段时设责任人，落库并在详情页显示名字；
2. `special` 弹窗没有阶段责任人下拉，接口直传别人的 `who` 被落回 `null`；
3. 阶段责任人登录 → 承接台「我负责的阶段」看到该条，且只勾得动自己那段；
4. 阶段责任人勾完 → 总负责人打开详情，看到 `doneBy` + `doneAt`；
5. 阶段责任人的日历上出现该阶段，别人的阶段不出现；
6. 老数据（无 `who`）打开详情、日历、进度与改动前一致（回归）。
