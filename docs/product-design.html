1
产品概述
背景 · 定位 · 目标 · 设计原则

1.1 背景与问题

公司业务规模扩大后，任务分发长期依赖口头、IM 群聊与个人备忘录，缺乏统一的线上载体，带来四类典型问题：

任务下发无标准

起止时间、达成标准凭口头约定，事后无据可查，责任边界模糊。

进度不透明

管理者无法实时掌握下属任务的推进状态与常规工作的完成情况，只能逐人追问。

常规工作靠记忆

每月 / 每周 / 每日固定节点的事项（例会、报表、巡检）极易遗漏，且无人提醒。

承接链路断裂

上级下派的任务到管理者手中后，缺少「接收 → 规划 → 拆分 → 转入执行」的规范通道。

1.2 产品定位

面向组织的任务协作工作台：线上任务发放、项目管理、待办管理、日历调度的一体化平台。一期面向初级管理者，其角色同时具备三重能力：

向下可管

对下属

制定项目任务、划分阶段、设定达成标准，下发并跟踪进展；只读查看下属常规工作推进情况。

向内可管

对自己

自建月 / 周 / 日常规工作；自建专项工作并拆分阶段计划；随手创建临时任务。

向上可接

对上级

接收上级下派任务，规划拆分后移入专项或临时任务执行，进度回传上级。

1.3 建设目标

便捷

录入成本极低：常规工作自动实例化、临时任务 10 秒创建、任务拖拽改期。

高效

日历成为统一调度入口，四类任务自动汇入，自动识别工作日并避开法定节假日。

可管理

状态全程可查、闭环可追溯、下属进展一览；为后续员工版、中高层版复用底座。

1.4 设计原则

  • 任务单一实体、四类型统一建模：任务制定 / 常规 / 专项 / 临时共用一套任务模型与状态机，避免四套系统并行，为多角色版本复用预留基础。
  • 日历即调度入口：一切任务自动汇入日历与今日待办，任务与日历双向即时同步（同一实体、无副本），改任一侧全局生效。
  • 状态机统一、可扩展：以「待开展 / 进行中 / 已完成 / 暂缓」四状态为基座，逾期、待验收等以派生标签实现，不破坏主状态。
  • 先管理闭环、后报表分析：一期聚焦「发 → 接 → 做 → 报 → 查」全链路，统计报表与组织级看板留给中高层版。
  • 数据可迁移、权限可扩展：独立部署，组织架构可导入；RBAC 预留 admin / manager / employee 三级角色位。

1.5 一期范围与边界（2026-10-30 评审确认）

本节逐条锁定一期的「做 / 不做」，评审与验收以本节为准，防止范围漂移。未列入的动作一律视为不做。

范围项一期做法不做 / 后续
登录注册工号 + 姓名，免密码，与后台花名册（工号唯一、姓名一致）匹配即通过。不做密码、不做短信验证码、不做 SSO；二期视推广范围接企微扫码或 OA 单点。
通知与提醒仅站内：「打开即见」——首屏今日待办、导航徽标、临期 / 逾期标记。不做邮件、不做企业微信、不做 App 推送；二期首项接企微工作通知。
汇报关系用户自选，一个直属上级，即选即生效，可在设置里随时自查与修改。不做审核、不做管理员纠偏、不做虚线上级、不做跨级下发。
任务验收四状态（待开展 / 进行中 / 已完成 / 暂缓），执行人标记完成即完成。不做「待验收 / 退回重做」，不作为绩效考核依据。
组织架构管理员导入 Excel 花名册 + 用户自选上级，两者拼接成组织树。不接 HR 主数据、不接企微通讯录、不做自动同步。
移动端不单独适配；手机浏览器可打开查看。不做移动端专属交互（日历拖拽在手机不可用）、不做小程序 / App。
报表与导出仅页面内的完成率、阶段进度等即时统计。不做组织级看板、不做 Excel / PDF 导出、不做数据接口。
免密登录可以被接受的前提 免密意味着「知道同事工号与姓名就能登入」，所以它成立有三个硬条件，缺一条就要改方案：
① 本期不含高敏数据——只有任务、日程、常规节点，没有薪资、身份证、合同。这是能免密的最主要原因。
② 有访问日志——每次登录记录工号 / 时间 / IP / 设备，出现冒用可追溯、可一键停用。
③ 试点人群可控——一期只开通试点部门，不做全员开放；正式全员推广前必须补 SSO 或企微扫码。
没有推送，靠什么让人打开 这是本产品最大的落地风险：待办类工具一旦没人主动打开，两周就死。一期的三条对策——
① 首屏零点击：登录后第一屏就是今日待办，手机上也是第一屏，不需要找入口；
② 管理者驱动：周会过进度就用这张表，下属为了不被问住会自己进来看，靠管理动作带使用；
③ 视觉不靠推送：待接收任务在导航上挂红点计数，逾期在列表与日历上标红，打开一眼能看到该干什么。
这三条能撑住试点，但撑不住全员推广——二期必须接企微推送。

用户角色与核心场景
一期角色边界 · 核心场景与功能映射

2.1 角色定义（一期）

角色职责边界权限要点
初级管理者（本方案主角色）双身份：对下属是任务下发者 + 监督者；对自己是任务执行者（承接上级任务 + 自身专项 + 常规工作）。管理本人全部数据（增删改查）；只读查看直接下属的下发任务进展与常规工作推进情况；承接上级下派任务。
组员（普通员工）一期以最小集存在：接收任务、更新进度、自建自身常规工作、创建临时任务。完整员工版在二期深化。仅见本人任务与本人常规工作；对管理者下发任务可上报进度。
上级（中 / 高级管理者）一期以「下派任务」的发起方存在：向初级管理者下派任务，查看其承接进度。下派任务；查看被下派任务的执行状态（完整中高层版在二期深化）。

2.2 核心场景与功能映射

核心场景用户诉求对应功能
月初制定项目任务，划分阶段，设定起止时间与达成标准，下发给组员一次把任务说清楚、留痕可追踪任务制定与管理
每月 5 号例会、每周一报表、每天 9:00 巡检等固定节点事项不遗漏固定事项自动出现、自动避开节假日常规工作管理
上级下派一个大任务，需要自己拆解规划再执行承接 → 规划 → 拆分 → 移入专项 / 临时任务承接台
临时被安排一件事，先记下来别忘10 秒内创建，默认出现在今日待办临时任务
在日历上看本周安排，把冲突的任务拖到别的日期日历驱动、拖拽改期、双向同步日历待办
看看组员的任务做到哪一步了一览直接下属的任务与常规进展任务制定-跟踪
设计口径一期角色互动的核心是「初级管理者」这一个角色位，但数据模型与权限骨架按三角色设计，确保二期「普通员工版」、三期「中高层版」可以直接在底座上扩展，不做推倒重来。

3.1 模块 6 命名建议

模块 6 负责「接收上级下派任务 → 规划 → 拆分 → 移入专项 / 临时任务执行」，是组织任务链路上行的关键一环。命名建议：

候选名理由评价
任务承接台「承接」同时覆盖接收与承担两层含义，与「任务制定（下发）」构成下发 / 承接的对称关系，语义完整、职场通用。推荐
任务受理台偏「受理」语义，更接近客服工单语境，弱化了「自己还要承担执行」的意味。备选
上派任务直白但只描述了来源，未体现「规划拆分与转入执行」的动作。备选
承接中心同上，与「专项 / 常规」命名体系略不一致。备选
待拍板产品正式名称与模块 6 名称将在评审会确认，本方案统一暂用「任务承接台」。

3.3 功能域与需求映射表

功能域需求要点（原文）设计方案要点
1 任务制定与管理制定项目任务、划定起止与达成标准、下发组员；可选阶段性目标；查看下发任务进展与下属常规工作推进情况。任务 = 基本信息 + 达成标准 + 阶段列表；阶段为可选（阶段名 / 起止 / 达成标准 / 状态）；下发后进入组员待办；跟踪页提供列表 / 看板双视图；下属常规工作以只读汇总卡呈现。
2 常规工作管理自定月常规、周常规、日常规；即固定时间 / 固定节点要做的事。规则化建模（frequency + 节点 + 提醒时间），系统按周期自动实例化为待办任务；遇法定节假日自动向前排。
3 专项工作管理管理者定义自身非常规工作规划，可自行拆分、做阶段计划、设起止时间。专项 = 管理者自己的「迷你项目」：可拆阶段 / 子任务，每项独立起止与状态；阶段计划视图呈现推进。
4 临时任务新建临时任务，可设起止时间；建议放在今日待办。入口置于今日待办顶部「+ 新建」；默认当天起止、默认分类「其他」；创建即进日历。
5 日历待办日历形式，支持任务待办管理、安排；常规 / 专项 / 临时任务自动出现，双方即时更新。月视图为主（周 / 日可切）；四类任务按类型着色自动展示；任务与日历同实体双向同步；支持跨日拖拽改期；工作日 / 节假日标注。
6 任务承接台接收上级下派任务并拆分规划；可移入专项 / 临时任务中工作。待接收 / 已接收 / 已拆分三区；接收后可规划拆分成子任务；一键移入专项（复杂项目）或转为临时任务（单点事项）；执行状态回传上级。
7 设置（支撑）任务分类两级、由管理者自行设置；优先级 / 重要度 / 紧急度可选填。两级分类树管理；优先级 = 重要度 × 紧急度（1–3 级，可选，默认中 / 中）。

4.3 其余页面结构要点

列表 / 看板双视图

常规工作页

日 / 周 / 月三 Tab

专项工作页

卡片墙 + 阶段计划

专项卡片含进度条与起止；详情页纵向阶段计划（阶段名 / 起止 / 状态 / 达成标准），每阶段下挂子任务清单。

任务承接台

三区布局

1 待接收：上级下派任务列表（可拒收并回理由）；2 已接收：规划拆分画布（拆出子任务、设阶段与起止）；3 已拆分：子任务去向（移入专项 / 转为临时），并同步回传上级。

设置页

分类树 + 偏好

两级分类树管理（增删改、排序）；优先级说明；成员与组织（一期导入）；提醒偏好（提醒时间、通道开关）。

5.3 常规工作建模：规则 → 实例

regular_rule（规则模板）

frequency（day / week / month）+ 节点（weekday 1–7 或 day_of_month 1–31）+ notify_time + holiday_policy（默认 forward 前移）。一条规则可只含一个节点（如「每月 5 号部门例会」），也可含一组节点（如「月度薪酬工作」= 本月 28 日发核薪邮件 / 次月 1 日交工资初稿 / 次月 10 日做绩效分析 / 次月 15 日发工资）；每个节点独立配置月份（本月 / 次月）、日期、时间与节假日策略（2026-10-30 增补跨月）。

regular_instance（实例）

按周期自动生成（每日定时任务扫描）：生成未来 N 天实例并挂接 task_id（即成为一条常规类型任务，自动汇入今日待办与日历）。多节点规则的实例是一个「周期容器」，各节点带自己的日期与完成状态，日历上按节点日期分别落位；节点全部完成则实例完成。跨月周期：节点声明 month_offset（0 = 本月，1 = 次月），周期锚点取起始节点所在月，因此一个周期可以横跨两个月（如 10-28 → 11-13），实例的 start / end 自然跨月。完成 / 改期后不再重复生成；实例状态独立于规则。

设计要点常规实例本身是 task（type=regular），因此「待办、日历、状态机」完全复用主任务链路；同时通过 rule_id 反查规则，实现「改规则 → 仅重排今天以后未开始的实例」，历史实例保留；实例与节点可拖拽，但只改「本次」，规则本身不变（可一键恢复）。
改规则时，重排范围怎么定（2026-10-30 修正） 早期版本按「今天以后尚未开始的实例」重排，遇到跨月规则会出错：本周期可能从 10-28 就开始，改动后 start 已过，旧排期不会被清掉，而新排期又因周期 ID 已被占用而生成不出来——用户看到的是「改了规则，日历没变」。据此改为按周期归属月判断：
① 重排范围——本月及以后的所有周期实例，无论是否已完成，一律删除重建。理由是规则一改，周期边界本身就可能变（5 日起 vs 28 日起），旧排期不再成立。
② 历史保留——本月之前的周期实例原样保留，作为历史记录，不会被改写。
③ 勾选恢复——重排前记录已勾选的节点名称，重建后按名称恢复，但只恢复日期已过（≤ 今天）的节点，避免把新排期里还没到的节点误标成已完成。
④ 跨月实例的 key——实例 ID 仍为 ri_<rule>_<周期月>，一个周期只有一条实例，避免同一周期出现两条重复记录。
规则停用 / 删除时，已生成的实例怎么处理（2026-10-30 补充） 实例是规则的投影，规则一改口径，实例的处理必须显式说清，否则用户会看到「规则删了、日历里还在」的怪象：
① 停用——不再生成新实例，已排的实例保留；卡片上标注「已停用，共 N 条实例仍在日历中」，并给出「清空实例」按钮作为出口。
② 删除（默认）——连同该规则生成的全部实例一起删除，日历与今日待办立即干净；删除前弹窗明示「已生成 N 条实例，其中 M 条未完成」。
③ 删除（可选）——用户也可以选「只删规则，保留 N 条实例」：实例脱钩为独立记录（不再关联规则、不再生成新的），详情页注明「所属规则已删除」，可单条删除。
④ 数据自愈——若历史数据里存在「规则已不存在但实例还挂着」的脏数据，登录时自动清理并提示清理条数；用户主动选择保留的实例打「脱钩」标记，不参与自愈清理。

5.4 优先级设计（重要度 × 紧急度）

优先级为可选填字段，不强制；未填写时按「中 / 中」处理。排序规则：先按重要度、再按紧急度；展示为四象限定位。

重要 · 紧急

立即执行，今日优先；典型：上级急派、上线阻塞项。

重要 · 不紧急

规划执行；典型：专项阶段、重点项目任务。

不重要 · 紧急

快速处理或委派；典型：临时事务、催办。

不重要 · 不紧急

碎片时间处理；典型：资料整理、例行归档。

5.5 账号、身份与汇报关系（2026-10-30 评审确认）

一期不接 SSO / OA 单点，采用工号 + 姓名作为登录凭据；汇报关系由用户首次登录时自选，用来点亮「下属可见性」与「任务承接」两条链路。本节定的是模型与口径，不涉及具体实现。

项目规则
登录凭据工号 + 姓名，需与后台花名册（工号唯一、姓名一致）匹配方可通过；不匹配直接拒绝并提示「请与管理员核对工号姓名」。一期确认免密（2026-10-30 评审），成立前提与风险缓解见 1.5；免密仅限试点范围，全员推广前须补 SSO / 企微扫码。
首次登录进入「选择直属上级」引导页，可按工号 / 姓名搜索；允许跳过。跳过者可正常使用「对自己」的功能（今日待办、常规、专项、临时、日历），但下发任务与任务承接台不可用，顶部常驻提示「未设置上级，承接链路未开启，点此设置」。
汇报关系模型一个直属上级（user.manager_id 单值自环）。不是多个，理由见下方说明。
防环校验不能选自己；不能选自己的任意层级下属（A→B→A 的环直接拒绝并提示原因）；一人只有一个上级，试点期被选者无需确认（二期改为需上级确认，避免「单方面认领领导」）。
花名册维护一期由 HR 指定 1 名管理员，用 Excel 导入并每月更新一次；离职当天停用账号（停用后其下发任务保留 90 天可查），调岗由管理员改部门字段。不做自动同步。
变更与留痕可在「设置 → 我的汇报关系」修改，变更写入 org_change_log（操作人、时间、原上级、新上级）。已发生的下发任务保留原上级可见，新增任务只对新上级可见。
可见范围以「自己」为根向下遍历组织树，一期只到直接下属（1 层），不递归到孙级；跨部门、跨层级一律不可见。这条同时约束「下发任务进展」与「下属常规工作」两类数据。
为什么是「一个上级」而不是多个 1. 责任唯一——下发任务必须有唯一的验收人，多上级最容易出现「都以为对方在跟」的扯皮；
2. 可见范围可算——权限按组织树层级收敛，多父节点会让可见集变成并集而膨胀。一个初级管理者若能自选 5 个上级，等于拿到半个公司的可见权；
3. 自选可控——MVP 的上级是用户自己选的，单上级把「自主扩权」的口子缩到最小；
4. 可扩展——真实的矩阵汇报（多头汇报、项目线汇报）用虚线上级承载：二期加 user_dotted_manager（0..n），只授予只读查看，不参与任务下发与验收。数据模型留了位置，不阻断一期上线。
一期明确不做 汇报关系审核与管理员纠偏（自选即生效，选错由本人自查改正）、跨级下发（给下属的下属直接派活）、虚线上级（多上级）、组织架构自动同步（HR 主数据 / 企微通讯录）。一期组织树由「管理员导入 Excel 花名册 + 用户自选上级」拼接而成；二期再接 HR 主数据，届时自选上级自动降级为异常兜底。

6.3 双向同步与日历拖拽规则

规则说明
同一实体、无副本任务在「列表 / 日历 / 今日待办」三处展示的是同一个 task 记录：改日历 = 改任务起止；改任务状态 = 日历即时变色。天然满足「双方即时更新」。
拖拽范围制定 / 专项 / 临时任务支持跨日拖动；常规实例与多节点规则的单个节点也可拖，但只改「本次」（规则不变，卡片标「日期已调整」，可在详情一键恢复）。
拖拽校验跨日移动时：目标日期早于今天且未开始 → 提示；拖过原截止日 → 提示并可选「同时顺延截止日」；与已有任务冲突 → 仅提示不拦截（多任务并行为常态）。
拖拽落库整体平移起止（跨日任务保持时长）；写 task_log 审计（谁在何时把任务从 X 日拖到 Y 日）；走事务 + 乐观锁。
待办栏 ↔ 日历今日待办栏中的任务可直接拖入日历未来日期（相当于改期）；日历中的任务可拖回待办栏（回到今天）。

6.4 任务分类规则

  • 分类为两级树（一级如：产品 / 研发 / 运营 / 市场 / 管理…；二级如：产品 › 需求 / 设计 / 评审…），由管理者在设置中自定义（增删改、排序）。
  • 系统预置默认分类树，落地后各管理者可按团队习惯调整；删分类时已有任务迁移到父级或「其他」。
  • 临时任务创建时默认分类 =「其他」（不可为空，可再修改）；任务制定下发时分类必选。

6.5 权限与可见性（一期）

数据对象权限规则
本人全部数据初级管理者可完整管理自己的任务、常规规则、专项与临时任务（增删改查）。
下发任务对直接下属下发任务的进展、状态、阶段进度只读可见（按组织树层级收敛，跨部门不可见）。
下发任务在本人日历 / 待办的呈现下发任务的执行人是下属，因此不进入管理者的日历与今日待办，避免占用管理者日程；管理者只在「任务制定」中以列表 + 阶段进度跟踪（2026-10-30 评审确认）。
下属常规工作（默认态）只读查看直接下属的常规工作推进情况；看板默认折叠为一行汇总（今日完成率 / 本周达成率 / 最近完成时间），不展开节点明细，避免管理者被细节淹没。
下属常规工作（关注后）管理者可对某成员下的某条常规工作点「关注」，该条在看板上展开：多节点规则（如月度薪酬工作）直接显示当前所处节点——节点名 / 计划日期 / 完成状态 / 是否因节假日改期；单节点规则展开后显示该节点的日期与完成状态、以及最近一次完成时间。关注是管理者本人的视图偏好，不通知下属、不改下属任何数据。
下属常规工作（编辑权）规则与节点的编辑权永远不下放：管理者只能看执行状态，不能改下属的规则、节点日期或完成标记。
汇报关系与可见范围一人一个直属上级（user.manager_id），可见范围按组织树向下 1 层收敛；未经设置上级的账号不可下发与承接（详见 5.5）。
承接链路上级下派任务仅「本人 + 上级」可见；拆分子任务归属本人管理。
角色位RBAC 三段：admin / manager / employee。一期启用 manager + employee 最小集，admin 由系统管理员。

6.6 提醒设计（一期仅站内，2026-10-30 确认）

一期不做任何外部推送：无邮件、无企业微信、无 App 通知。提醒以「打开即见」为原则落在界面上，不依赖推送通道。

今日待办（首屏）

登录后第一屏即今日待办，零点击可见：今日到期任务、今日常规节点、待接收的上级任务。

导航徽标与红点

「任务承接台」显示待接收数量角标；逾期任务在列表与日历上标红，打开一眼能看到该干什么。

临期标记

剩余 ≤3 天标「剩 N 天」，已过期标「逾期 N 天」；仅做视觉提示，不打断操作、不弹窗。

这条的代价必须写进预期 不做推送，打开率完全依赖人的习惯。试点期靠两件事撑住：管理者在周会上用这张表过进度（下属为了不被问住会主动打开），以及首屏零点击的今日待办。但推广到全员时必须先接企微推送，否则使用率会断崖式下跌——这是二期第一优先级。

8.3 工业级健壮性要求

并发与一致性

task.version 乐观锁防多人同时编辑覆盖；状态流转接口幂等；拖拽改期走事务；常规实例化按「规则 + 日期」唯一约束幂等。

权限安全

后端行级校验（责任人 / 下发人 / 直属上级），前端隐藏仅是体验、后端拦截才是底线；越权访问一律 403；防注入 / 防 XSS / 防 CSRF。

审计留痕

task_log 记录关键操作：创建 / 下发 / 状态变更 / 拖拽改期 / 分类调整；可追溯「谁在何时改了什么」。

数据可靠

每日自动备份 + 保留策略（本地 + 异地）；迁移脚本先演练后上线；节假日表变更走版本化数据迁移。

规则引擎测试

节假日前移、补班识别、跨月滚动、提醒去重等规则用单元测试覆盖（fixture 用例），不依赖人工抽查。

性能预算

单月视图任务渲染控制在 500 条内分页 / 懒加载；今日待办接口 < 200ms；日历拖拽交互本地乐观更新 + 后台确认。

分期路线与里程碑
一期初级管理者版 → 二期普通员工版 → 三期中高层版
一期
约 4–6 周
初级管理者版（本方案范围）

工号 + 姓名免密登录与自选直属上级、任务制定与下发（含阶段目标）、常规工作（日 / 周 / 月 + 多节点 + 节假日自动前移）、专项工作（阶段拆分）、临时任务、日历待办（拖拽 + 工作日识别）、任务承接台、下属常规工作折叠与关注、两级分类、优先级、站内提醒（不做邮件 / 企微 / 推送）、Excel 花名册导入。

二期
约 4 周
普通员工版

第一优先级：接企业微信工作通知与待办卡片（不解决推送，全员推广会失败）；组员接任务、报进度、自建自身常规工作与临时任务；下发任务的验收确认流；免密升级为 SSO / 企微扫码；统计口径完善。

三期
中 / 高级管理者版

组织级看板与报表（完成率、逾期率、人效）、跨部门任务协调、审批流、移动端适配强化。基于一期底座扩展，不做重构。

建议一期建议按「数据模型与权限骨架 → 核心闭环（制定 / 常规 / 临时）→ 日历与拖拽 → 承接台」的顺序推进，每两周一次可演示增量，先跑通单团队试点再推广。

10.1 已确认（评审结论）

#决策项结论
1模块 6 命名采用「任务承接台」（与「任务制定」语义对称）。
2常规工作遇普通周末与法定节假日一致前移；规则内可按节点配前移 / 顺延 / 跳过。
3账号与组织架构来源工号 + 姓名免密登录；Excel 花名册导入 + 用户自选直属上级；不接 HR 主数据 / 企微通讯录。
4达成标准的验收流程一期不做验收：执行人标记完成即完成，不作为绩效考核依据；验收流放二期。
5提醒通道一期仅站内：无邮件、无企业微信、无 App 推送；打开即见（首屏 / 徽标 / 临期标记）。
6日历是否对接公司日历一期独立日历；对接单独评估。
7「向前排」口径节点落在假期段中间时，前移至假期段前最近工作日（每月 5 号，假期 3–7 号 → 2 号）。
8优先级是否必填可选填，默认「中 / 中」；不填不影响使用。
9下属常规工作可见粒度默认折叠为汇总；可对单条「关注」展开；多节点规则显示当前节点。只读，编辑权不下放。
10汇报关系数量一个直属上级（manager_id 单值），不做虚线上级。
11自选上级是否审核不审核、不纠偏：即选即生效，本人可在设置里自查修改。
12是否允许跨级下发不允许：只能给直接下属派活。
