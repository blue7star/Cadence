# G2 复核清单

> 给**没参与实现**的人或新开的对话用。按顺序过，每条都要有结论（通过／不通过／不适用）。
> 清单里的每一条都对应 `issues.md` 里真实踩过的坑，不是通用模板抄来的。

## A. 先确认「评的是哪版代码」

| # | 检查 | 怎么查 | 为什么有这条 |
|---|---|---|---|
| A1 | 工作区里有没有混进与本次无关的改动 | `git status --short`，逐个问「这行为什么在这里」 | #9：七个版本堆在工作区没提交，混在一起后无法判断哪条改动属于哪次需求 |
| A2 | 上一轮的改动提交了吗 | `git log --oneline -3` 与契约的树摘要对得上 | 同上。没提交的改动一旦被覆盖就没了 |
| A3 | 验的是不是当前代码 | `curl -s localhost:8788/api/version` 的 `semver` 是否等于 `version.js` 的 `SEMVER` | #11：e2e 跑的是服务启动时的旧代码，还报全绿 |
| A4 | 门禁摘要与交付段一致 | `_dev/verify-report.json` 里的 `digest` 是否等于契约第 2 段记录的 | 防止「拿 A 版代码的证据评 B 版代码」 |

## B. 不变量有没有被破坏

| # | 检查 | 怎么查 |
|---|---|---|
| B1 | 老数据库还能打开吗 | 备份 `data/workbench.db`，用旧库启动，登录、看日历是否正常 |
| B2 | 常规实例生成是否幂等 | 连续两次触发 `maintain`，实例条数不变 |
| B3 | 可见性四视角 | 依次切成 本人／下属／上级／无关同事，确认该看的能看、不该看的看不到，且只读页面真的不能改 |
| B4 | 日期算法边界 | 跨月（26 日起）、月末 31/30/28、闰年 2/29、周末与节假日、阶段跨月连续 |
| B5 | 状态与节点对齐 | `done` 全勾、`todo` 全放、`doing`/`paused` 至少留一个未完成；日历与清单说法一致 |
| B6 | 逾期判定 | 计划结束日已过且未完成 = 逾期；**已完成永不算逾期** |
| B7 | 同步冲突 | 两个标签页改同一条任务，先看谁覆盖谁，再对照契约里写的语义 |

## C. 证据是不是真的

| # | 检查 | 怎么查 | 为什么 |
|---|---|---|---|
| C1 | 断言有没有被放宽 | `git diff HEAD -- _dev/e2e.mjs`，看有没有删断言或改期望值 | 让测试变绿最省事的办法就是改测试，这是最隐蔽的自欺 |
| C2 | 视觉结论是量出来的还是看出来的 | 断言里是否有 `getComputedStyle` 的具体颜色值 | #14：截图看浅色小字看错过好几次 |
| C3 | 失败信息能否定位到函数 | 故意改坏一处，跑一次，看报错是否指出「哪个函数算错了」 | 报「界面不对」等于没报（#12） |

## D. 收尾

| # | 检查 |
|---|---|
| D1 | `issues.md` 里这次涉及的问题，状态更新了吗？新问题登记了吗？ |
| D2 | `fail_source` 标对了吗？同一个标记连续出现两次，规则要改，不是代码要改 |
| D3 | 使用者能感知到的变化，`version.js` 的 Z 位 bump 了吗？`--write` 跑了吗？ |
| D4 | 契约第 3 段填完了吗？（未填 = 这次复核没发生） |
